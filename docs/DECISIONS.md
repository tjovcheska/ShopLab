# Decisions

Choices made where PLAN.md was ambiguous or where the toolchain forced a choice. Newest last.

## Phase 1 — Project setup

- **Prisma 7.10.1, not npm `latest`.** When this was built, npm's `latest` tag for Prisma pointed at a release candidate (8.0.0-rc). The plan asks for stable tools, so we pinned the newest stable release. Prisma 7 requires a driver adapter (`@prisma/adapter-better-sqlite3`) and keeps the database URL in `prisma.config.ts` rather than in `schema.prisma`. The generated client is written to `src/generated/prisma`, which is gitignored and recreated by `postinstall`.
- **Next.js Cache Components turned off.** Next 16.4 turns on `cacheComponents` by default, and it has two effects we don't want. First, every database read needs `"use cache"` or a `<Suspense>` boundary. Second, visited routes stay in the DOM as hidden `<Activity>` trees. That would give Playwright locators duplicate, invisible matches from earlier pages, which is confusing for students. With it off, pages call `connection()` (or read cookies) and render on every request.
- **No Google Fonts.** `next/font/google` downloads fonts at build time, which fails in offline Docker or CI builds, so pages use the system font stack.
- **No `.env` needed.** The acceptance command (`npm install && npm run db:reset && npm run dev`) has no step that copies `.env.example`. So `DATABASE_URL` falls back to `file:./dev.db` in both `prisma.config.ts` and `src/lib/db.ts`.
- **Deterministic seed details.** Ids restart at 1 on every seed, products have fixed `createdAt` dates one day apart, and passwords are hashed with a fixed bcrypt salt, so even the hashes match between runs. A fixed salt is only acceptable because the demo passwords are public.
- **Product images.** These are generated SVG placeholders in `public/products/<slug>.svg`, created by `scripts/generate-product-images.ts` and committed to the repo.
- **Enums.** `User.role` and `Order.status` are Prisma enums. SQLite supports them in Prisma 6.2 and later.
- **Prices.** Shown in USD (`$12.34`).
- **Header placeholders.** In Phase 1 the cart count is always 0 and the header always shows "Log in". Phase 2 connects both to the session.

## Phase 2 — Authentication

- **Stateless signed sessions.** The `shoplab_session` cookie holds `base64url({ uid, exp }).HMAC-SHA256`, signed with `SESSION_SECRET`. The server keeps no session table, so a database reset doesn't log anyone out: seeded users keep the same ids. Sessions last 7 days. In Phase 8 the same token can be sent as a bearer token. Without `SESSION_SECRET`, a fixed development secret is used.
- **Cookie flags.** `httpOnly`, `sameSite=lax`, `path=/`, and **not** `secure`. ShopLab runs over plain http on localhost, in Docker, and in CI. Browsers don't store secure cookies on a plain-http host such as `http://shoplab:3000` inside docker-compose.
- **Real 403 status.** Admin pages call `forbidden()`, which needs Next's experimental `authInterrupts` flag. The alternative was rendering a "forbidden" message with status 200, which would make `response.status()` assertions meaningless. `forbidden.tsx` can't set its own `<title>`, so the admin page's `generateMetadata` returns "Access denied" for non-admins.
- **Anonymous visitors on admin pages** are sent to `/login?next=…`, like any protected page. Only logged-in customers get the 403.
- **Admin page.** No admin pages existed yet, so `/admin` was added as a small dashboard of counts to demonstrate the 403 behavior.
- **Register asks for a full name** as well as email and passwords, because `User.name` is required.
- **Password rule.** At least 8 characters and at least one digit. Shared zod rules in `src/lib/validation/auth.ts` run in the browser and again in the server action. Client checks run on submit, then live while the user fixes errors. Both forms use `noValidate`, so the browser's native validation bubbles never appear.
- **Login errors.** Unknown email and wrong password both show "Invalid email or password."
- **Forms are submitted manually** (`onSubmit` → `startTransition(formAction)`) rather than relying only on `<form action>`. React resets a form after its action runs, which would clear typed values when the server returns errors. The `action` attribute stays, so forms still work with JavaScript disabled.
- **Safe `next` redirects.** `next` must be a same-site path (`/…`, not `//…` or a full URL); anything else falls back to `/account`. Logged-in users who open `/login` or `/register` are redirected straight on.

## Phase 3 — Catalog and product pages

- **Chaos controls built here.** PLAN.md lists chaos as a global convention without assigning it to a phase, and Phase 3's acceptance ("skeletons appear when a delay is set") needs it. So this phase adds the shared helper (`withChaos()` in `src/lib/chaos.ts`), the `/chaos` panel, and the yellow banner. Priority is: `?delay` on the URL, then the cookie, then the env var. Chaos cookies are not `httpOnly`, so tests can set them with `context.addCookies()`.
- **`?delay` on a page reaches the API through `apiFetch()`** (`src/lib/api-client.ts`), which copies the page's `?delay` onto every `/api/...` call. Only API responses are delayed. Server-rendered pages (home, product detail) are not.
- **The product list API is `GET /api/v1/products`,** the Phase 8 endpoint, built now so it isn't written twice. It uses Zod validation and the standard error format (400 `VALIDATION_ERROR` with per-field details).
- **Query parameters are the same on the page and the API:** repeated `category=<slug>`, `minPrice`/`maxPrice` in whole dollars (inclusive), `inStock=true`, `sort` (`name-asc` default, `name-desc`, `price-asc`, `price-desc`, `rating-desc`), `page`, and on the API only `pageSize` (1–100, default 12). Every sort falls back to name and id, so order is deterministic.
- **Filter UX.** Every filter change pushes a new URL (so Back works) and resets to page 1. Controls use `useOptimistic`, so a checkbox shows as checked as soon as it's clicked, even with navigation still in flight. Without this, Playwright's `check()` failed with "did not change its state".
- **Price range.** Two native range sliders, `$0` up to the most expensive product rounded up to $10, in steps of $5. The URL updates **300 ms after the last change** (debounced), so dragging doesn't fire a request for every step.
- **The "In stock only" toggle** is a checkbox with `role="switch"`.
- **Add to cart works now, but only when logged in.** Anonymous users go to `/login?next=<current page>`. It's a minimal server action that checks stock against what is already in the cart, then refreshes the header count. Phase 5 builds the cart page on top of it. Feedback is an inline `role="status"` or `role="alert"` message under the button. Phase 4 adds toasts.
- **Pagination links** are real `<a href>` links named "Page N" (with `aria-current="page"` on the current one), plus Previous and Next. On the first and last page, Previous and Next are non-link text with `aria-disabled`.

## Phase 4 — Search and dynamic elements

- **Search matches product names only** (case-insensitive "contains", using SQLite `LIKE`), both in autocomplete and on `/search`. Matching descriptions made suggestions confusing: "co" matched "cotton" and "colour". The list API gained a `q` parameter and a `newest` sort.
- **Autocomplete suggestions** come from `GET /api/v1/products?q=…&pageSize=6`, so chaos delay and flaky mode apply. Only results for the text currently typed are shown. While a request is in flight, a "Searching…" status shows instead of stale suggestions.
- **Mouse highlighting uses `onMouseMove`, not `onMouseEnter`.** Otherwise a cursor resting where the list opens highlighted an option, and `Enter` opened that product instead of searching. That bug showed up in testing.
- **`/search` is server-rendered** and lists every match (no pagination, since there are only 40 products). With JavaScript off, the header form still submits to it.
- **No `<Suspense>` around the header search box or the chaos banner.** Content inside a Suspense boundary is streamed hidden and revealed by a script, so with JavaScript off the search form was invisible. Every route renders dynamically, so `useSearchParams` works during server rendering without Suspense.
- **Toasts** live in a provider in the root layout and are removed exactly 3 s after they appear (one timer each). They stack, and each can be dismissed. Only _successful_ add-to-cart uses a toast; errors stay as an inline `role="alert"` next to the button.
- **Infinite scroll** uses an IntersectionObserver on a sentinel below the list. The observer is re-created each time a page finishes loading. A new observer reports the sentinel's current position, so very tall windows keep loading until the sentinel is off-screen, with no scroll-position maths. There is no auto-retry on error; a "Try again" button is shown.
- **New arrivals** waits a random 1000–3000 ms, then fetches the 4 newest products from the API. This is the only random timing in the app, apart from flaky mode. If the fetch fails, the widget never appears.
- **Live stock** re-fetches `GET /api/v1/products/:id` (Phase 8's endpoint, built now). Each refresh is scheduled 5 s after the previous one _finishes_, so chaos delays never stack up requests. On failure the last value stays, with a "Retrying…" note.

## Phase 5 — Cart and checkout

- **The payment iframe (`/embed/payment`) is built here, not in Phase 6.** Phase 5's acceptance needs an end-to-end purchase, and the plan puts payment inside that iframe. It already behaves as Phase 6 describes: the card form is inside the iframe, the result goes to the parent with `postMessage`, `4242 4242 4242 4242` succeeds, and `4000 0000 0000 0002` is declined with the error shown only inside the iframe. Any other well-formed number is declined as "not recognized". Phase 6 still adds nested frames, new tabs, popups, and dialogs.
- **A paid order can only come from the iframe.** The iframe asks the server to authorize the card and gets back a signed payment token (15 minutes, tied to the user and the exact amount). `placeOrder` checks the token, refuses a different amount ("pay again"), and marks it used only after the order is saved. A failed order (for example, out of stock) doesn't use up the payment. Used payment ids are kept in memory, which is fine for a fake provider. The checkout page only accepts `postMessage` from its own iframe (`event.source`) on the same origin.
- **Shared token signing.** `src/lib/signing.ts` signs both sessions and payment tokens. The signature includes a purpose, so one kind of token can't stand in for the other. Changing the format logged out existing sessions once.
- **Schema additions.** `Order.shippingCents` and `Order.deliveryMethod` were added, which go beyond PLAN.md's model. Without them, the confirmation page couldn't show the shipping cost or method. `totalCents` is still items plus shipping. Seeded orders use standard and express delivery.
- **`npm run db:migrate` now also runs `prisma generate`.** Prisma 7's `migrate dev` no longer regenerates the client, so new columns were missing from the TypeScript types.
- **Cart requires login** (anonymous visitors go to `/login?next=/cart`). Steppers go from 1 to the product's stock and update instantly (`useOptimistic`). Use "Remove" to take a line out entirely. The remove confirmation is a native `<dialog>` opened with `showModal()`, which gives a real modal (focus trap, Escape, `role="dialog"`). If stock falls below a cart quantity, the cart shows an alert and hides "Proceed to checkout".
- **Wizard state stays in the browser** until "Place order". Nothing is saved per step, and reloading the page restarts checkout. Each step has an `h2` that receives focus when the step changes. Back is disabled on step 1.
- **Countries and regions.** The native `<select>` offers US, Canada, UK, and Germany. The custom region dropdown is the ARIA "select-only combobox" pattern (`div role="combobox"` + `div role="listbox"`), so `selectOption()` doesn't work on it. Changing the country clears the region.
- **Delivery.** Standard costs $4.99 and Express $14.99; the method sets the price and the date is chosen separately. The earliest date is the first weekday at least 2 days after the browser's today. The latest is today + 60 days. Weekends are disabled. Dates travel as `YYYY-MM-DD` strings and are stored as midnight UTC. The server accepts a date that is valid for the day before or after its own date, to allow for time zones. Tests that fake the browser clock (`page.clock`) are still checked against the server's real date.
- **The date picker** is a button that opens a non-modal `role="dialog"` calendar (a `<table>` of day buttons named like "Wednesday, November 25, 2026"). Disabled days are real `disabled` buttons. Opening moves focus to the selected or first available day. Escape (from anywhere) or a click outside closes it.
- **Changing the delivery method after paying** changes the total, so the payment no longer counts and the iframe reloads for the new amount. After approval the iframe stays visible with its own "Payment approved" message.
- **Order numbers** are `SL-` plus the zero-padded id (`SL-000003`). Orders are created as `paid`.
- **The confirmation page** is `/orders/[id]?placed=1` (the `?placed=1` adds the "Thank you" message). Customers can only open their own orders (others get 404); admins can open any.
- **Fresh header after ordering.** `placeOrder` ends with `revalidatePath("/", "layout")` plus `redirect()`. Without that, the root layout isn't re-rendered on navigation and the header still shows the old cart count.
- **Dev-mode collisions.** `devIndicators: false` in `next.config.ts` removes the Next.js dev tools button, whose name "Open Next.js Dev Tools" made `getByRole('button', { name: 'Next' })` match two buttons in `npm run dev`. The order status badge uses `data-order-status`, not `data-status`, because the Next.js dev error badge also has a `data-status` attribute.
- **No site chrome inside embeds.** `/embed/*` pages render without the banner, header, and footer (`src/components/site-chrome.tsx`), because they're shown inside iframes.

## Phase 6 — Frames, tabs, and popups

- **The payment iframe was already built in Phase 5** (see above) and behaves as this phase specifies. This phase adds the other frames, tab, popup, and dialog pages.
- **`/playground` index page.** The header has linked to it since Phase 1, so a minimal index now lists Frames and Dialogs. Phase 7 adds the remaining playground pages to the same list.
- **Frames playground.** `/playground/frames` holds an "Outer frame" containing an "Inner frame", plus a "Sibling frame" next to it. Each frame has its own `title` and `name`, so students can locate frames by title, by name, or through the Frame API (`page.frame({ name })`, `parentFrame()`). Frame pages live under `/embed/frames/*` so they render without the site header.
- **The size guide link is on every product page.** PLAN.md doesn't limit it to clothing, so the simplest option was to show it everywhere. It opens `/size-guide?product=<slug>` with `target="_blank" rel="noopener"`, so the new tab has no `opener`. The size guide is a normal page with the site header.
- **Share popup.** "Share" calls `window.open('/popup/share?product=…', 'shoplab-share', 'popup,width=480,height=560')`. The popup keeps `window.opener`. "Share to the ShopLab feed" sends a `postMessage` to the opener, which shows a toast, and then the popup closes itself. That gives students a full two-window flow: wait for the popup, act in it, wait for it to close, assert on the original page. `/popup/*` pages render without the site header. "Copy link" uses the Clipboard API, so tests need clipboard permissions. If the popup is blocked, the product page shows an alert.
- **Dialogs playground.** It uses real `window.alert`, `confirm`, and `prompt` (default value "Guest") and writes each outcome to a "Result" line. Playwright's `dialog.accept()` with no argument behaves differently per browser (checked in Phase 7): Chromium and WebKit submit an **empty** prompt, while Firefox keeps the default value. Use `dialog.accept(dialog.defaultValue())` to get the same result everywhere. Dialogs with no handler are dismissed automatically.

## Phase 7 — Playground for advanced UI

- **Drag and drop uses native HTML5 events only** (`draggable`, `dragstart`, `dragover`, `drop`), with no library, so Playwright's `dragTo()` exercises real browser drag and drop. `dataTransfer.setData()` is always called because Firefox won't start a drag without it. In the sortable list, dropping an item on another moves it into that position. On the board, dropping a card anywhere in a column moves it to the bottom of that column. Every item also has buttons ("Move Apples up", "Move “…” to Done") so the page works without a mouse.
- **`<shoplab-rating>` builds its shadow DOM once and updates it in place,** so clicking a star doesn't destroy the focused button. It's defined in the browser only (dynamic import), because it extends `HTMLElement`. Changes fire a `rating-change` event with `bubbles` and `composed` so the page can hear it. There are two instances ("Product quality", "Delivery speed") with identical button names, so tests must scope to one component first. `src/types/custom-elements.d.ts` teaches TypeScript the JSX tag.
- **Uploads really reach the server** (a Server Action) and are discarded after reporting each file's name and size. There's a 2 MB limit per file. The Server Action body limit is raised to 10 MB in `next.config.ts` (the default is 1 MB). An empty file input still submits a 0-byte entry whose name arrives as `"undefined"`; those entries are ignored, so "Upload" with no file shows "Choose at least one file first."
- **The download link** points to `GET /api/playground/download`. It returns a CSV of all products with `Content-Disposition: attachment; filename="shoplab-products.csv"` and goes through `withChaos()`, like every API route.
- **The data table** has 12 fixed customers, including two "Alex Smith" and two "Sam Lee" rows that only the email tells apart. Sorting toggles ascending and descending per column and sets `aria-sort` on the header. Ties keep the original order. The filter matches name, email, plan, or city. Selection survives filtering, and "Select all" acts on visible rows only and shows the indeterminate state for partial selection.
- **Hover-only UI** is hover-only on purpose: clicking or focusing doesn't open it, as PLAN.md asks. Two techniques are mixed: CSS-hidden elements that are always in the DOM (the menus, the "Returns policy" tooltip, the hover-card buttons) and a tooltip mounted only while hovered ("Shipping info"). That lets students see the difference between "hidden" and "not attached".
- **Visibility examples** show how Playwright's rules play out. `hidden`, `visibility: hidden`, and zero size count as not visible; `opacity: 0` and an element at `left: -9999px` **count as visible**. The covered button makes `click()` fail with "intercepts pointer events" until the overlay is removed. `aria-disabled="true"` counts as disabled for Playwright, just like the `disabled` attribute.
- **The Phase 6 pages were re-checked in Chromium, Firefox, and WebKit** once the browsers were installed. One fix came out of it: the share popup's buttons are now **disabled until React has hydrated**. In Firefox, a test that clicked "Close" right after the popup opened sometimes hit the server-rendered button before its click handler existed, so nothing happened. Playwright waits for a button to be enabled before clicking, so the race is gone.

## Phase 8 — REST API

- **One wrapper for every endpoint.** `apiRoute()` (`src/lib/api/route.ts`) adds chaos (`withChaos`), turns a thrown `ShopError` into `{ "error": { code, message, details? } }` with its status, and turns anything else into `500 INTERNAL_ERROR`. Route handlers only parse input, call a service, and serialize the result.
- **Shared services.** The rules for users, the cart, orders, products, and reviews live in `src/lib/services/*`, and the web UI's Server Actions were refactored to call the same functions. The API and the website can't disagree, and the UI kept its exact messages (the Phase 2–7 checks still pass).
- **Cookie or bearer, same token.** `Authorization: Bearer <token>` is checked first, then the `shoplab_session` cookie. Both carry the same signed session token, so a token from `POST /auth/login` also works as the cookie, and the website's cookie works in API calls. A Bearer header that is present but invalid gives 401; it doesn't quietly fall back to the cookie. Login and register don't set a cookie, they only return the token.
- **Error codes.** `VALIDATION_ERROR` and `INVALID_JSON` (400); `UNAUTHORIZED` and `INVALID_CREDENTIALS` (401); `FORBIDDEN` (403); `NOT_FOUND` (404); `EMAIL_TAKEN`, `SLUG_TAKEN`, `INSUFFICIENT_STOCK`, `CART_EMPTY`, `ALREADY_REVIEWED`, `PRODUCT_HAS_ORDERS` (409); `CHAOS_FLAKY` and `INTERNAL_ERROR` (500). Order-specific 400s are `INVALID_SHIPPING`, `INVALID_DELIVERY`, and `PAYMENT_DECLINED`. Validation errors list fields in `details.fields`, for example `"shippingAddress.region"`.
- **Paying for API orders.** The web checkout pays only through its iframe, but an API client has no iframe. `POST /orders` therefore takes the test card details in the body (`4242…` approved, `4000…0002` declined) and reports a decline as `400 PAYMENT_DECLINED`. 402 would be more conventional, but the plan's status list doesn't include it. `delivery` is optional and defaults to standard delivery on the earliest valid date. Orders are always created from the caller's cart, as on the website.
- **`POST /cart/items`** returns 201 for a new cart line and 200 when it increases an existing one. `:id` in `/cart/items/:id` is the cart item id, not the product id.
- **`PUT /products/:id` replaces the whole product.** Optional fields left out go back to defaults: slug from the name, rating 3, placeholder image. Products in any order can't be deleted (`409 PRODUCT_HAS_ORDERS`), so order history stays intact. Cart lines and reviews are deleted with the product.
- **One review per user per product** (`409 ALREADY_REVIEWED`). Reviews don't change a product's `rating` field, which stays as seeded.
- **Someone else's order is 404, not 403,** so order ids can't be probed. Admins can read any order. `GET /orders` always lists only the caller's own orders.
- **JSON only.** A catch-all route returns a JSON 404 for unknown `/api/v1/...` paths instead of the HTML 404 page. A wrong method on a known path gets Next.js's default 405.
- **The OpenAPI document is a TypeScript object** (`src/lib/openapi.ts`) with a custom `x-access` field (`public`, `user`, or `admin`). It's served at `/api/v1/openapi.json` and rendered server-side at `/api-docs` with no external scripts or CDN. It has to be kept in sync with the routes by hand. The Phase 8 check compared every status the API actually returned with the documented ones.

## Phase 9 — Test support endpoints

- **Every `/api/test/*` endpoint, health included, is a JSON 404 unless `TEST_HOOKS_ENABLED=true`.** PLAN.md lists health among the gated endpoints, so the environment that Playwright's `webServer` or CI waits on must enable test hooks (Phase 10's Docker setup does). Any other `/api/test/...` path is also a JSON 404.
- **Test hooks are exempt from chaos.** `testRoute()` skips `withChaos()`, so `?delay`, the chaos cookies, and `CHAOS_*` env defaults never slow down or break a health check or a reset. Errors use the same JSON shape as `/api/v1`.
- **One seed implementation.** The seed data and loader moved to `src/lib/seed/` and are used by both `npm run db:seed` and `POST /api/test/reset`. The reset runs in **one transaction**, so it's all-or-nothing and fast. bcrypt hashes of the seed passwords are cached in memory after the first reset. Measured on the production build: about 240 ms for the first reset after a server start, about 10 ms afterwards. On `npm run dev` the first call also compiles the route, taking about 1.5 s. After a reset, the SQL dump is byte-identical to a fresh `npm run db:seed`.
- **Sessions survive a reset.** Seeded users keep their ids, and tokens are stateless, so storage states for seeded users stay valid. A token for a user created by a test can, after a reset, match a different user who later gets the same id. Avoid reusing such tokens across resets.
- **`POST /api/test/users`.** Every field is optional (`email`, `password`, `name`, `role`). Random credentials still meet the site's password rules, so the UI login form accepts them. It returns `{ user, credentials, token }` with 201. A duplicate email is `409 EMAIL_TAKEN`.
- **`POST /api/test/products`** accepts one object or an array of up to 50. Every field is optional with defaults: price 1000 cents, stock 10, rating 3, the first category, and a placeholder image. `categorySlug` can be used instead of `categoryId`. Products are created one at a time, so if one fails (for example `409 SLUG_TAKEN`), the products before it stay created.
- **`POST /api/test/login-as`** sets exactly the same `HttpOnly` session cookie as the login form (shared `SESSION_COOKIE_OPTIONS`) and also returns the token. In Playwright, `context.request.post('/api/test/login-as', …)` followed by `context.storageState()` gives a logged-in state without filling in the form.
- **`GET /api/test/health`** runs `SELECT 1` and returns exactly `{ "status": "ok" }`. If the database is unreachable it returns 503 `{ "status": "error" }`.

## Phase 10 — Docker, environments, and smoke test

- **Base image `node:22-bookworm-slim`, not Alpine.** better-sqlite3 ships prebuilt glibc binaries. The `deps` stage still has `python3 make g++` as a fallback in case one has to be compiled. The final image doesn't include them.
- **Three stages:** `deps` (`npm ci`), `build` (`prisma generate` + `next build`), `runner`. The runner keeps dev dependencies, because the container runs `prisma migrate deploy` and the tsx-based seed on every start. Image size was traded for simplicity.
- **Every container start runs migrations, then the seed, then `next start`** (`scripts/docker-start.sh`). Each environment gets its own fresh SQLite file at `/data/shoplab.db` inside its container. There's no volume, so data never leaks between restarts or environments. The script puts `node_modules/.bin` on `PATH`, because `prisma db seed` runs the bare command `tsx`. That only works inside `npm run`, and the first test run caught it.
- **The container runs as the non-root `node` user.**
- **Compose environments.** `shoplab` (port 3000, chaos off) and `shoplab-staging` (port 3001 on the host, port 3000 inside, `CHAOS_DELAY_MS=500`) share one image, `shoplab:local`. Only `shoplab` builds it, and staging reuses it. Both set `TEST_HOOKS_ENABLED=true` (the health endpoint needs it, see Phase 9) and a fixed `SESSION_SECRET`, which is fine for local practice environments. Compose healthchecks call `/api/test/health` with Node's `fetch`, so no `curl` is needed in the image.
- **The smoke test is a separate npm package** in `smoke/` with its own `@playwright/test` (1.65.1), lockfile, and `node_modules`. The app's dependencies and the students' test folders stay untouched. It's excluded from the root `tsconfig.json` and ESLint config. It has one Playwright project per environment (`local`, `staging`), with URLs overridable through `SMOKE_LOCAL_URL` and `SMOKE_STAGING_URL`. Run it with `npm run test:smoke`.
- **`docs/ci-example.yml` is documentation, not an active workflow.** It starts compose, polls both health endpoints for up to 2 minutes, runs the smoke test, uploads the report and prints container logs on failure, and always runs `docker compose down`.
- **Verified with Docker 29 and Compose 5.8 on Colima (linux/arm64).** The image is about 1.8 GB, mostly `node_modules` with dev dependencies, which a slimmer image could drop by running the seed without tsx. Both containers reached "healthy" within the first healthcheck checks after starting, and the smoke test passes against both.

At the instructor's request, every playground feature now lives in the normal shop flow, and the isolated `/playground` pages (and `/embed/frames/*`, `/api/playground/download`) were **removed**. PLAN.md still describes Phase 7's playground; this section records the deviation.

**Hydration fix, found while testing these features.** In Firefox and WebKit, Playwright could type into a server-rendered **controlled** input before React hydrated it. React kept the text on screen, but its state stayed empty, so the next re-render (typing in another field) wiped the input. This had been latent since Phase 2: the login email was lost in 5 of 6 Firefox runs, and the card number in 2 of 6 WebKit runs. `useAdoptDomValue()` (`src/lib/use-adopt-dom-value.ts`) copies the DOM value into state on mount. It's used by `FormField` (login, register, payment, checkout shipping), the search box, the quantity input, the verification code, the admin filter, and the country select, and it brought the loss rate to 0 in 10 of 10 runs in every browser. The register and shipping forms now use functional state updates, so several adopted fields don't overwrite each other. Clicks before hydration can still do nothing, so `<html data-hydrated="true">` (`src/components/hydration-marker.tsx`) gives tests a documented signal to wait for.

**Review form after posting.** `ReviewForm` stays mounted for logged-in users and decides itself whether to show the form, "Thanks!", or "You have reviewed this product." Otherwise the server refresh after posting replaced it before the thank-you message could be seen.
